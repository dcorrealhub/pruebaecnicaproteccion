# Resumen de hallazgos — Módulo de aportes voluntarios

Versión corta y en lenguaje sencillo de [HALLAZGOS.md](HALLAZGOS.md), donde está el detalle técnico de cada punto.

**Gravedad:** 🔴 Crítica: puede descuadrar dinero o filtrar datos; impide aprobar el cambio · 🟠 Alta: fallará en uso normal; hay que corregirla antes de salir · 🟡 Media: hay que planificar su corrección · ⚪ Baja: orden y legibilidad del código.

| ID | Gravedad | Dónde está | Qué pasa | Ejemplo de lo que puede salir mal | Cómo lo corregiría |
|---|---|---|---|---|---|
| H-001 | 🔴 Crítica | Consulta de aportes (`AporteController`) | La consulta a la base de datos se arma pegando directamente lo que escribe el usuario. | Al escribir `x' OR '1'='1' --` como identificador del afiliado, la respuesta trae **los aportes de todos los afiliados**. *Comprobado.* | Pasar los datos del usuario como parámetros separados de la consulta, usando el método del repositorio que ya existe para esto. |
| H-002 | 🔴 Crítica | Registro de aportes (`AporteService`) | El límite mensual de 10 millones solo se revisa cuando el total da **exactamente** 10 millones. | Un afiliado con 4,5 M aporta 6 M, llega a 10,5 M y **se acepta**. Otro que llega justo a 10 M es rechazado. *Comprobado.* | Rechazar el aporte cuando el total **supere** el límite, y no solo cuando sea igual. |
| H-003 | 🔴 Crítica | Registro de aportes y tabla de saldos | Si llegan dos aportes del mismo afiliado al mismo tiempo, ambos leen el mismo saldo y el segundo borra la suma del primero. | 50 aportes simultáneos de $1.000 deberían sumar $50.000, pero el saldo quedó en **$9.000**. También permite saltarse el límite mensual. *Comprobado.* | Bloquear el saldo mientras se actualiza, o hacer la suma directamente en la base de datos en una sola operación. |
| H-004 | 🔴 Crítica | Registro de aportes | El registro guarda tres cosas (saldo, evento y aporte) por separado. Si la última falla, las dos primeras ya quedaron guardadas. | Se cae la base de datos al guardar el aporte. El saldo ya subió y la auditoría dice «registrado», pero el aporte no existe. El cliente reintenta y el saldo sube dos veces. | Guardar las tres cosas como una sola operación: se guardan todas o no se guarda ninguna (`@Transactional`). |
| H-005 | 🔴 Crítica | Montos en todo el módulo | El dinero se guarda en un tipo de número que no es exacto con decimales y que acepta «infinito». | Diez aportes de $0,10 dan un saldo de $0,9999999999999999. Un aporte de `1e400` **se acepta** y el saldo del afiliado queda en «Infinito» para siempre. *Comprobado.* | Usar un tipo numérico exacto para dinero (`BigDecimal`), con decimales fijos, y rechazar montos sin sentido. |
| H-006 | 🔴 Crítica | Búsqueda del saldo del mes | El saldo debería ser por mes, pero se busca solo por afiliado, sin mirar el mes. | Los aportes de octubre de 2026 se suman al saldo de junio de 2025. El «límite mensual» se vuelve un límite de por vida. Si existe el saldo de dos meses, el afiliado **ya no puede aportar** (error). *Comprobado.* | Buscar el saldo del afiliado **en el mes actual**, crearlo si no existe y evitar en la base de datos que haya dos del mismo mes. |
| H-007 | 🟠 Alta | Consulta de aportes (`AporteController`) | La capa que recibe las peticiones web habla directamente con la base de datos, saltándose las capas que deberían hacerlo. | Cualquier cambio en la base de datos obliga a tocar la capa web. Las reglas futuras de seguridad o auditoría no aplicarían a esta consulta. Así fue como se coló el H-001. | Mover la consulta a la capa de servicio y repositorio, y que la capa web solo reciba la petición y devuelva la respuesta. |
| H-008 | 🟠 Alta | Registro de aportes | No hay forma de reconocer que una petición repetida es la misma. | El usuario da doble clic, o la app reintenta porque la red tardó, y el aporte **se registra dos veces**. | Que cada aporte llegue con un código único de operación. Si el mismo código se repite, devolver el aporte ya registrado en lugar de crear otro. |
| H-009 | 🟠 Alta | Todo el servicio | No se verifica quién hace la petición ni si tiene permiso sobre ese afiliado. | Cualquiera puede ver los aportes de otra persona cambiando el identificador en la URL, o registrar aportes a nombre de otro. | Exigir autenticación (token) y comprobar que el usuario solo opere sobre los afiliados que le corresponden. |
| H-010 | 🟠 Alta | Fecha y periodo del aporte | La fecha se toma de la hora del servidor, que puede estar en otra zona horaria, y se consulta dos veces. | Un aporte hecho el 30 de junio a las 8 p. m. (hora de Colombia) queda registrado como de **julio**, y cuenta para el límite del mes equivocado. | Tomar la hora una sola vez y siempre en hora de Colombia. |
| H-011 | 🟠 Alta | Pruebas automáticas | Las pruebas solo revisan el caso en que todo sale bien. | Todos los errores críticos anteriores existen y **las pruebas pasan en verde**: nadie se habría enterado. | Agregar pruebas del límite mensual, del saldo después de registrar, de aportes simultáneos, de fallos a mitad del registro y de la consulta web. |
| H-012 | 🟡 Media | Datos de entrada del registro | No se validan los datos que envía el cliente. | Se aceptan aportes sin afiliado, con un canal inventado («cualquier cosa») o sin monto. | Declarar qué campos son obligatorios y qué valores son válidos, y rechazar la petición antes de procesarla. |
| H-013 | 🟡 Media | Respuestas de error | Cuando algo está mal (monto negativo, afiliado inexistente, límite superado) el servicio responde «error interno del servidor». | La app no puede decirle al usuario qué hizo mal, y el monitoreo se llena de falsas alarmas. | Responder con códigos claros: dato inválido, no encontrado o regla de negocio incumplida, con un mensaje entendible. |
| H-014 | 🟡 Media | Respuesta del servicio | Se devuelve el registro interno de la base de datos tal cual. | Se exponen datos internos, como la marca de «en revisión». Cualquier cambio en la base de datos cambia la respuesta y puede romper a los clientes. | Definir un formato de respuesta propio, con solo los datos que el cliente necesita. |
| H-015 | 🟡 Media | Estructura de la base de datos | Las tablas se crean automáticamente, sin reglas que protejan los datos. Además, se borran al apagar la aplicación. | Nada impide en la base de datos montos negativos, campos vacíos o dos saldos del mismo mes. | Definir las tablas con scripts versionados que incluyan esas reglas (obligatorios, únicos, montos positivos). |
| H-016 | 🟡 Media | Registro de auditoría | El evento de auditoría no dice **qué** aporte se registró ni **quién** lo hizo, y se escribe antes de confirmar el aporte. | Ante un reclamo, no se puede reconstruir quién registró qué aporte. La auditoría puede decir «registrado» de un aporte que nunca existió. | Guardar primero el aporte y luego la auditoría, con el número del aporte, el usuario, el canal y un identificador para rastrear la operación. |
| H-017 | 🟡 Media | Configuración | Solo existe la configuración de desarrollo: base de datos en memoria, consola de base de datos abierta y datos de prueba. | Si se despliega así, cada reinicio borra todos los aportes y se cargan afiliados de prueba. | Separar la configuración de desarrollo y la de producción, con las credenciales fuera del código. |
| H-018 | ⚪ Baja | Clases de datos (`Aporte`, `Saldo`, `EventoAporte`) | Cualquier parte del código puede cambiar libremente el saldo o el monto. | Hoy no causa errores, pero facilita que alguien modifique el saldo sin pasar por la regla del límite. | Que el saldo solo se pueda modificar mediante una operación que aplique las reglas, por ejemplo «acreditar aporte». |
